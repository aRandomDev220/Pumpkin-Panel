# Phase 7 (Updates + Operational Polish) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Safe Pumpkin image updates with rollback, user administration, audit visibility, manager self-recovery, and an accessibility/responsive pass — shippable operational polish.

**Architecture:** Updates run as `update`/`rollback` task types through the existing runner: preflight (policy, disk, backup presence) → pull in background → stop → recreate same data → readiness → rollback on failure with the previous image kept. Manager DB restore stages a validated file applied on next boot (never a live swap). New admin UI follows a written design plan that extends the existing dark-minimal language.

**Tech Stack:** Rust Axum + existing `bollard`/`tokio`; React 19 + TanStack Query; no new dependencies.

**Spec:** `pumpkin-manager-implementation-plan.md` (§11.4 image flow, §17.2/17.6 API, §25 Phase 7, §27–28 releases/docs); trust boundaries §5.3/§12.

## Global Constraints

- Rust edition 2021; `cargo fmt --check` clean; `cargo clippy -p pumpkin-manager-backend --all-targets -- -D warnings` clean (documented `allow`s only).
- TypeScript strict; no `any`; `npm run build --prefix apps/web` clean.
- TDD: failing test first, watched fail, minimal code, full-suite green.
- Stub + `mod` for `update_service.rs` pre-wired in BASE. Task 1 alone creates `migrations/0007_update.sql` and edits `task_runner.rs`; Task 2 alone edits `routes_admin.rs` (+ `docs/backup-restore.md`, new file ok). Task 3 owns listed frontend files; Task 4 runs AFTER Task 3 and may edit them. Implementers NEVER edit `Cargo.toml`, `main.rs`, or another task's files.
- SQL bind-only. Never log image pull tokens (none exist), passwords, or DB contents. Permission changes always audited.
- Commit ONLY the task's own files; `feat:` prefix. No-subagents contract.
- `main.rs` route wiring + DB pending-restore boot swap are the controller's job — handlers standalone `pub async fn` taking `State<AppState>`.

## Review Focus

- Update races a concurrent backup/restore on the same server (Task 1 owns: test — op-lock makes the second 409).
- Pull of a malicious/typosquat image outside the allowlist (Task 1 owns: test pins allowlist rejection before any pull).
- Rollback after the new version mutated world data still restores the OLD container+image but must warn data-format is one-way (Task 1 owns: test pins the warning text in the rollback result).
- Restoring another manager's DB file (different schema version) bricking this manager (Task 2 owns: test — user_version newer/older than supported range → rejected pre-stage).
- A viewer reaching user-admin or audit endpoints (Task 3 owns: UI hides + tests? UI can't test perms — backend 403s already covered; Task 3 documents the mapping instead).

**Interfaces:**
- Consumes: `RuntimeAdapter` (pull via `Docker::create_image`? — `DockerAdapter` has no pull method; add `pub async fn pull_image(&self, reference: &str)` on `DockerAdapter` in `runtime.rs` — Task 1 MAY edit `runtime.rs` for this method + its unit test only), `task_runner` task transitions, `enqueue_backup` in `routes_backup.rs` (read-only reference — call it for the mandatory pre-update backup), `readiness::ping_java` for post-update readiness, `AppState::op_locks` pattern (read-only reference).
- Produces (exact signatures for Task 3's UI + controller wiring):
  - `pub async fn preview_update(pool, server_id, image_reference: &str, image_digest: Option<&str>) -> Result<UpdatePreview, UpdateError>` with `pub struct UpdatePreview { pub warnings: Vec<String>, pub resolved_digest: Option<String>, pub current_reference: String }` — no pull, no mutation. Warns (never blocks except invalid): unpinned tag (no digest), image outside allowlist → error not warning, unknown Pumpkin profile for the target, no verified backup present.
  - `pub async fn enqueue_update(pool, adapter: Option<&DockerAdapter>, server_id, requested_by, image_reference: &str, image_digest: Option<&str>, allow_without_backup: bool) -> Result<String, UpdateError>` (returns task_id; `409 UPDATE_NO_BACKUP` unless a completed verified backup exists for the server or the flag is set; `422 INVALID_IMAGE` outside allowlist)
  - `pub async fn enqueue_rollback(pool, adapter, server_id, requested_by) -> Result<String, UpdateError>` (`409 NO_ROLLBACK_TARGET` when `previous_image_reference` empty)
  - Handlers: `preview_image_update` (`POST /servers/:id/update/preview`), `update_server` (`POST /servers/:id/update` → 202), `rollback_server` (`POST /servers/:id/rollback` → 202). Controller applies `ServerUpdate` layers.
  - Worker steps (inside `update` task execution): op-lock → preflight (disk ≥ 2× data dir size, else fail) → protected auto-backup via `enqueue_backup`-equivalent internal call (same code path, reason `pre-update`) → pull image in worker → stop container → remove container → create with NEW image (persist `previous_image_reference/digest` FIRST, then swap `image_reference/digest`) → start → readiness (inspect running + 20s ping window) → success clears... no: KEEP previous ref for future rollback (only overwritten by the next update) → audit every step. On ANY failure after remove: recreate+start with previous image, run readiness, task message states whether rollback succeeded; data-format one-way warning ALWAYS in rollback messages.
  - Migration `0007_update.sql`: `ALTER TABLE servers ADD COLUMN previous_image_reference TEXT NOT NULL DEFAULT ''; ALTER TABLE servers ADD COLUMN previous_image_digest TEXT NOT NULL DEFAULT '';`

  - `docs/backup-restore.md`: manager DB backup/restore/recovery procedure (download, staged restore + restart, pre-restore copies, what to do when locked/corrupt) + server world consistency model pointer (existing behavior, no new claims).
